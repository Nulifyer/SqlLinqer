SqlLinqer design and performance review

Keep the model-driven interface. Make query meaning, SQL compilation and execution separate responsibilities. Correctness across dialects is the first priority; reusable plans and typed readers are the next performance investment.

The design is useful. Its execution model needs consolidation.

SqlLinqer lets developers define tables and relationships in C# models, compose explicit SQL-style queries through typed member paths, and load nested graphs through database-generated JSON. The central idea is control over query shape with reusable model conventions.

Implemented within the current major

Implementation branch: feature/compatible-query-improvements. Existing public methods, connector subclasses, response types and runtime targets remain available. A reflection comparison against the base commit found all 1,223 existing public/protected contract entries unchanged. The only added public property is ConnectorOptions.UseSqlModelJsonContract.

  • Relationships: member paths distinguish repeated joins, and configured default schemas flow to child and linking tables. Explicit schema mappings win.
  • Query results: automatic paging preserves grouping and distinct projections. Counts retain result shape and avoid the previous duplicate predicate bindings. PostgreSQL DISTINCT JSON projections use jsonb for comparison, following the PostgreSQL JSON documentation.
  • Inserts: execution batches respect parameter budgets and SQL Server row limits. Batches share a transaction, combine outputs and keys, and preserve caller ownership. Owned failures roll back and return errors as values.
  • Rendering: CTE aliases are stable across repeated renders. Ordinary predicates avoid pairwise leaf scans and repeated snapshots. Column hashes are cached with checks for public metadata mutations.
  • Model caches: keys use actual runtime types, so identically named types in different assemblies remain distinct.
  • JSON: SQL-only loading is opt-in. Set UseSqlModelJsonContract = true to ignore API attributes. The default retains existing attribute-driven loading.

Verified: 430 regression checks, 100 native SQLite checks, 55 native DuckDB checks and 43 Azure-local checks passed. Both demo builds passed, including the .NET Framework target. PostgreSQL/MySQL live tests remain blocked by Docker socket permissions. Live SQL Server/Azure was not run.

Deferred: the compiler replacement, compiled queries, direct typed readers, async, cancellation, streaming and model analyzers. These remain separate feature work. No performance claim is made for database execution or JSON materialization.

Preserve

Model attributes, explicit graph selection, SQL-style query control, provider-independent core code and caller-owned transactions. The fluent interface can survive an internal redesign.

Repair first

Relationship identity, schema propagation, aggregate paging and totals, insert budgets and JSON name consistency. Incorrect results must be fixed before optimizing throughput.

My assessment

The largest structural gap is that rendering also discovers joins, adds projections, creates aliases and collects parameters. Shared mutable metadata and dialect-specific exceptions compound the problem. A small query compiler would give these decisions a defined home.

A compiler with typed results and explicit ownership

Approved design requirement: independent SQL and API contracts

SQL JSON is an internal wire format. Database loading follows SqlLinqer mappings and projection members. With UseSqlModelJsonContract enabled, API JSON attributes, converters, constructor annotations and application serializer options do not change SQL loading. The current major preserves legacy loading by default. A class can therefore serve as both a database model and an API model. Use SqlLinqer attributes for database behavior and JSON attributes for API behavior.

This requirement supersedes the earlier suggestion to align SQL output with API serialization names. The findings and test counts elsewhere remain the historical review snapshot.

Use a few deep modules with small interfaces. The stages below are conceptual; they do not require a full object graph copy at each step. Select a stage for its contract.

Preserve type information

Use typed column and expression references internally. Keep SQL nullability, result cardinality, constructor arguments and conversions in the plan. Separate database names and CLR projection members from API JSON names. The SQL model contract ignores API JSON attributes; legacy loading remains the default in this major. Provider values may still be boxed at the final binding seam.

Reduce fluent inheritance

Use composition for shared predicates, paging and projections. Separate ordinary writes from returned-row queries. Avoid repeating method families with hidden new members merely to preserve fluent return types.

Keep caches bounded

Offer explicit compiled queries first. Share templates, metadata and result readers. Keep values, closures, commands and transactions execution-local. Account for collection length when it changes SQL shape; do not use one template for incompatible parameter layouts.

Make dialect differences explicit

A dialect adapter should own syntax and capabilities, including returned rows, bulk inputs and pagination. Validate unsupported operations before execution. The existing Azure-to-SQL Server resolver is a useful start, but does not consolidate the other rendering branches.

Choose the loading strategy deliberately

Expected tradeoffs to measure, not measured winners
StrategyBest initial useCost to measure
Direct rowsFlat projections and returned keysReader-to-object conversions and per-row allocations; avoids the JSON serialization round-trip.
Nested JSONSelected graphs where one SQL statement is valuableDatabase JSON CPU, correlated work, payload size and buffering. SQL Server currently assembles the full JSON string.
Batched graph loadingGraphs with substantial collection fan-outExtra round trips, key buffers, merge lookups and consistency across statements. Batch by relation, not by parent row.

Define ordering, empty collection and absent-reference behavior for each strategy. Offer cursor paging with stable unique ordering for sequential browsing. Make exact totals opt-in and document the consistency contract between page and count queries.

Execution improvements

  • Centralize connection, command, transaction and reader ownership. Build on the existing ConnectionFactoryConnector for provider-specific authentication.
  • Add end-to-end async and cancellation where providers support them. DuckDB already has native timeout cancellation; that is different from a public asynchronous streaming contract.
  • Map rows and keys directly into their declared types. Cache accessors instead of reflecting on every value.
  • Construct immutable success/failure results once; preserve cancellation semantics. Keep diagnostic SQL formatting out of the execution path.
  • Retain the existing .NET Standard compatibility contract while evaluating a modern target for streaming and async disposal.

Deliver in stages, with evidence at each step

Use ordinary feature branches for changes that preserve existing contracts. The size of an internal rewrite does not determine the major version. The compiler redesign can move one query family at a time behind the current interface.

Choose the release by compatibility

Current major: correctness fixes, deterministic aliases, lower-allocation predicate processing and internal compiler or reader replacements that preserve supported behavior. Preserve public metadata objects through adapters where needed.

Additive features: explicit compiled queries, async methods, cancellation, streaming and typed execution or projection methods can ship in a minor release. Retain existing methods and connector subclass contracts. Add model diagnostics as optional warnings before making them build errors.

Major release: remove or change public methods, replace response types, require new abstract connector members, remove supported runtimes, or change documented mutation, transaction or loading behavior.

JSON compatibility: earlier regression tests explicitly required API JSON attributes to control database loading. The implemented isolation changes that behavior. To ship it within the current major, add an explicit SQL-isolated loading mode and retain the existing default. Make isolation the default in a major release. Implemented: ConnectorOptions.UseSqlModelJsonContract defaults to false; callers explicitly enable isolated loading.

These are release candidates, not a completed compatibility audit. Check source and binary compatibility, supported query results, transaction ownership, materialization and runtime support for each branch. The compatible work is on feature/compatible-query-improvements. No major version bump was made.

1 · Immediate

Make results and limits trustworthy

Fix F1/F2 relationship identity and schema context, F3/F4 paging and counts, F5 insert budgets, and F6 naming. Add focused regression cases plus engine-backed cases for relational behavior. Retain F9 ownership tests.

Exit check: joins remain independent; schemas resolve as declared; grouped/distinct totals and pages match reference SQL; every batch respects its budgets.

2 · Baseline

Measure before changing the execution engine

Benchmark cold compilation and repeated execution separately. Cover 10/100/1,000 predicates, large IN filters, flat reads, nested fan-out, returned keys and batches. Record allocations, GC, peak memory, database time, round trips and generated SQL.

Exit check: reproducible benchmark fixtures and agreed budgets. Compare identical semantics and datasets; no percentage targets invented from this review.

3 · First replacement

Move ordinary SELECT queries to the new compiler

Introduce immutable model maps, query-local IDs, a builder that freezes once, typed result shape and a deterministic writer. Keep the old fluent calls as an adapter. Then add aggregates, counts and pagination.

Exit check: equivalence against reference SQL across dialects; repeat compilation is deterministic; existing result contracts hold.

4 · Data flow

Add reusable templates and typed readers

Implement explicit compiled queries, fresh bindings per execution, direct row mapping, async/cancellation and streaming disposal. Introduce a bounded cache only after its reuse patterns are understood.

Exit check: concurrent template execution has isolated values; no retained request objects; early stream disposal closes owned resources.

5 · Relationships and writes

Unify graph loading, batches and dialect capabilities

Add measured JSON/batched strategies, then migrate insert/update/delete and typed returned rows. Evaluate reusable TVP types and native bulk adapters where justified.

Exit check: supported/rejected capabilities are documented per dialect and backed by real-engine tests. Phase out the old compiler after parity.

Start with one difficult fixture

Use an order with separate billing/shipping addresses, two child collections, a schema override, renamed result members, grouping and pagination. It exercises the places where the current design loses meaning across layers.

Keep the redesign proportional

Defer a general-purpose SQL optimizer, universal IQueryable support, elaborate type-state interfaces, source generation and pervasive pooling until a measured need justifies them. Begin with the supported query language and a small number of tested adapters.

What is distinctive, and what already exists

The core techniques have precedents. SqlLinqer's strongest distinction is its particular combination of model-owned query entrypoints, model-defined defaults, explicit relationship selection and database-generated nested results. This is a comparison judgment, not an exhaustive novelty claim.

Choose how much infrastructure you want to own

Continue the custom compiler

Choose this when exact query semantics and graph shaping are the product goal. Own dialect parity, conversions, batching, cancellation and long-term testing.

Prototype a LINQ to DB adapter

Choose this when preserving your model conventions matters more than owning SQL generation. Translate a small set of your attributes and query operations first. Compatibility is unproven.

Before committing to either direction, compare three real queries: a flat typed projection, a graph with two collections and custom relationship conditions, and a transactional batch returning keys. Include every required dialect. Check package/license/runtime compatibility separately. No alternative-library performance comparison was run here.

Position the project around predictable nested queries and explicit data loading. Attribute mapping and typed predicates are established capabilities. Correct semantics, understandable SQL and measured memory use are stronger reasons for someone to choose this library.

Source observations behind the architecture proposal

  • SqlLinqer/Queries/Core/SelectQuery.cs:290 combines SQL writing with join discovery, ordering and stash/restore.
  • SqlLinqer/Components/Modeling/Column.cs:10 hashes a string for each UUID getter access.

  • SqlLinqer/Connections/BaseConnector.cs:188 returns complete lists through synchronous JSON reading; SQL Server buffers its full document.
  • SqlLinqer/Queries/TypedExt/InsertWithPrimaryKeyQuery.cs:72 uses an intermediate List<object> for returned keys.
  • SqlLinqer/Connections/ConnectionFactoryConnector.cs:13 already provides a connection-factory seam worth retaining.
  • SqlLinqer/Connections/CommandDeadline.cs:10 already implements native DuckDB timeout cancellation.
