# Flat-read investigation

This experiment investigates flat-read execution and mapping. It leaves query construction, snapshot optimization, count queries, and server databases out of scope.
The investigation itself changed no production library code. Its recorded measurements predate the subsequent adoption helpers and diagnostics hooks in this worktree; each report retains the source hash it measured.

## Reproduce

Requires .NET 10 and Python 3. Run from the repository root:

```sh
python3 SqlLinqer.Comparisons.Investigations/run.py --verify \
  --output TestResults/flat-reads-verify.json
python3 SqlLinqer.Comparisons.Investigations/run.py \
  --output TestResults/flat-reads-investigation.json
```

The default measurement run uses 1,000 and 10,000 customers, added name widths of 0, 128, and 1,024 characters,
six modes, and five independent process samples per case. Each process warms five complete operations and measures five more.
The short verification run uses empty, single-row, and 37-row fixtures.
Reports are not overwritten. The runner preserves completion status and retains raw samples after failures.

All modes return the same flat DTO with `Id`, `Name`, nullable `Note`, and `Active`.
The model has no navigation collections. Two of every three fixture customers match the filter.
SQL and bindings are prepared before timing; query building and rendering are excluded.
Queries select identical logical fields and order by the unique root ID.
Every operation buffers a list and performs the same field-by-field fingerprint consumption.
Expected values come from fixture rules, independently of each query API.

Workers run sequentially in a deterministically shuffled order with tiered compilation disabled and connection pooling disabled.
Timing includes connection lifetime, SQL execution, model loading, and common consumption work.
Managed allocations use process-wide counters. Assertions and fingerprint formatting run outside timing.
The raw report retains SQL, package lock, SDK/runtime, environment, source hash, options, and every validated sample.

## Controls

- `native`: handwritten typed reader access and model construction. A specialized lower-bound control, not a generic mapper implementation.
- `tabular`: the existing public `ExecuteReaderListAsync<FlatRow>` against ordinary scalar columns.
- `json`: the existing public `ExecuteReaderJsonAsync<FlatRow>` with JSON generated by SQLite during the query.
- `json-standard`: the same generated JSON decoded by standard System.Text.Json with case-insensitive names and numeric-string handling.
- `stored-json`: the library JSON reader consumes previously materialized JSON stored in another fixture table.
- `stored-standard`: standard System.Text.Json consumes those same previously materialized JSON values.

Stored JSON is materialized during setup, outside all measurement processes.
Its table has the same root IDs, filter column, and ordered primary-key access.
It has a different storage layout, so subtracting stored-JSON time from generated-JSON time does not isolate the exact CPU cost of JSON generation.
Standard JSON controls also bypass connector response handling. Their timing differences are not pure converter microbenchmarks.

## Recorded findings

[Raw measurements](results/flat-reads-2026-10-22.json) contain 180 validated process samples across 36 cases.
All 18 short verification cases passed.
The recorded runtime was .NET 10.0.13 with SQLite 3.53.3.

For 10,000 fixture customers and a 128-character added name payload, 6,667 roots matched:

- The handwritten reader measured 9.029 ms and 2,760.0 KiB per operation.
- The existing library tabular mapper measured 12.745 ms and 3,387.1 KiB.
- The library JSON path measured 18.771 ms and 5,890.6 KiB.
- Standard decoding of generated JSON measured 14.511 ms and 5,577.4 KiB.
- Library decoding of stored JSON measured 16.033 ms and 5,890.6 KiB.
- Standard decoding of stored JSON measured 10.801 ms and 5,577.4 KiB.

The native library path also had lower median time and allocations than the JSON path at the other measured widths and fixture sizes.
This supports investigating an optional native path for flat typed selects using the existing mapper as a starting point.
The source also shows per-member reflection assignment in the SQL JSON converter, which is a candidate for profiling.
The experiment does not establish which internal operation accounts for each timing difference.

## Compatibility limits

These DTOs use ordinary integers and strings, nullable strings, a parameterless constructor, and matching SQL/CLR member names.
They do not prove equivalent behavior for partial selections, anonymous projections, constructor-only models, binary data, dates, enums, or provider-specific values.
The tabular mapper currently requires matching columns for all mapped scalar members; JSON loading can load a partial model.
Automatic dispatch to native loading therefore needs a separate compatibility design and tests.

Standard JSON is a control, not a drop-in replacement for the library SQL model contract.
Any optimization must preserve SQL loading independently of API JSON attributes, converters, and constructor configuration.

These timings are separate from the original cross-library baseline. Different DTOs, pre-rendered SQL, and different fixture storage make direct subtraction inappropriate.
The measurements use warm local SQLite with no concurrent requests. They do not measure server CPU or network traffic.
No production optimization or public API change was made as part of this investigation.
